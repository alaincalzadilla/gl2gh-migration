# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

PowerShell scripts (`gl2gh_scripts/`) that drive GitHub's `gh gl2gh` CLI extension to migrate
repositories from GitLab into GitHub, on top of GitHub's GEI ("Octoshift") migration engine. See
`README.md` for the full step-by-step usage walkthrough (prerequisites, env vars, and the exact
command sequence); this file focuses on how the scripts are built internally.

There is no build, lint, or automated test tooling in this repo (no package.json, no Pester
tests). The scripts are validated by running them against real GitLab/GitHub endpoints, and syntax
can be spot-checked with `[System.Management.Automation.Language.Parser]::ParseFile()`.

The root-level `groups.csv`, `projects.csv`, and `*.octoshift*.log` files (when present) are local,
untracked run artifacts generated by `gh gl2gh inventory-report` — they are not part of the
scripts and are not checked into git.

## The gl2gh pipeline (`gl2gh_scripts/`)

Three scripts meant to be run in order, all defaulting to the same input file, **`projects.csv`**
— the output of `gh gl2gh inventory-report` (columns: `group-path, group-name, project, url,
last-commit-date, repo-size-in-bytes, attachments-size-in-bytes, is-archived, mr-count`) with
`github_org, github_repo, gh_repo_visibility` columns appended by hand once you've decided where
each project lands on GitHub. Script 1 only needs `group-path` + `project` and ignores the rest;
scripts 2 and 3 additionally require the three `github_*`/`gh_repo_visibility` columns. There's no
shared schema/module between the three files — each independently validates its own required
columns (checking `$row[0].PSObject.Properties.Name`, or the raw header line if the CSV has no data
rows), so extra columns are simply ignored and adding/renaming a column means updating each script
that uses it.

Source-side calls go directly against the GitLab REST API (`api/v4`, `PRIVATE-TOKEN` header,
`Invoke-RestMethod`/`Invoke-WebRequest`) — no `gh` CLI dependency for GitLab reads. A GitLab
project is resolved by URL-encoding its full `group-path/project` namespace path and hitting
`GET /projects/:id` directly (GitLab supports the encoded-path form as a project ID), which avoids
a separate list-and-filter step.

1. **`1_migration_readiness_check.ps1`** — pre-migration gate. Validates `GITLAB_PAT` once against
   `GET /user` (a single PAT is valid for the whole GitLab server). For each project in
   `projects.csv`, resolves its ID, then checks paginated open merge requests (`state=opened`) and
   paginated pipelines in a non-terminal status (`created, waiting_for_resource, preparing, pending,
   running, scheduled` — GitLab CI pipelines cover both build *and* release, so there's no separate
   release-pipeline check). Exits non-zero only on missing env vars or PAT validation failure;
   per-project API failures are tracked as flags and folded into the final summary. Always prints a
   warning/success summary and exits 0 otherwise, leaving the decision to proceed with the caller.

2. **`2_migration.ps1`** — the actual migration runner, written to work as a GitHub Actions step.
   Validates `GITHUB_TYPE` (`GitHub` → `https://api.github.com`, or `GitHubDR` → requires
   `GITHUB_API_URL`), `GITLAB_SERVER_URL`, `GH_PAT`, `GITLAB_PAT` up front. Runs up to
   `-MaxConcurrent` (max 5) projects in parallel via `Start-Job`, each job shelling out to
   `gh gl2gh migrate-repo --gitlab-server-url --gitlab-group --gitlab-project --github-org
   --github-repo --target-api-url --target-repo-visibility` (plus `--use-github-storage` when
   `-UseGithubStorage`, default `$true`). `migrate-repo` reads `GH_PAT`/`GITLAB_PAT` directly from
   the environment, not via `gh auth login`. Per-project output is tee'd to
   `migration-<github_repo>-<timestamp>.txt` and streamed back to the console from the job's log
   file — background jobs return only a `{ MigrationSuccess = <bool> }` result object, so log noise
   never crosses the job boundary. A live status bar (`QUEUE | IN PROGRESS | MIGRATED | MIGRATION
   FAILED`) is redrawn on each poll (5s interval), and progress is continuously written to an output
   status CSV (`-OutputPath`, defaults to `repo_migration_output-<timestamp>.csv`) with
   `Migration_Status`/`Log_File` columns appended, so the CSV is always a live view of migration
   state. Success is determined by exit code **and** by grepping the job's log for `State:
   SUCCEEDED` (and rejecting `No operation will be performed`) — a nonzero exit alone isn't
   trusted. This log-grep heuristic has been confirmed to work against a real `migrate-repo` run.

3. **`3_post_migration_validation.ps1`** — post-migration diff check. For each row in
   `projects.csv` (needs `group-path, project, github_org, github_repo`), compares GitLab vs.
   GitHub: default branch, branch count/names, and per-branch commit counts + latest commit ID.
   Uses `gh api` (paginated via `--paginate --slurp`) for the GitHub side and raw GitLab REST calls
   (paginated by looping `page`/`per_page` until a short page) for the GitLab side. If the larger of
   the two branch counts exceeds `$BranchValidationThreshold` (10), only the default branch gets
   full commit-count/latest-ID validation (to bound API calls); otherwise every branch present on
   both sides is checked, with mismatches (branch present on only one side) logged as warnings and
   skipped rather than failing the run. Writes a running log to `validation-log-<yyyyMMdd>.txt`
   (shared across all projects in one run) and a `validation-<github_repo>.json` snapshot
   (`gh repo view --json createdAt,diskUsage,defaultBranchRef,isPrivate`) per project.

### Cross-script contract

- All three scripts default to `projects.csv` (override with `-CsvPath`); the required-column set
  is a superset as you move from script 1 → 2 → 3.
- Env var validation happens up front in each script and exits 1 with an explicit `[ERROR]` +
  "Set it using: ..." message — there's no shared validation helper, so the exact messages differ
  slightly per script even for the same var (e.g. `GITLAB_SERVER_URL`).
- Script 2 assumes `gh` is authenticated and has the `gl2gh` extension installed; script 3 assumes
  `gh` is authenticated for the target GitHub host (`gh api`, `gh repo view`) but talks to GitLab
  over raw REST, so it needs `GITLAB_PAT`/`GITLAB_SERVER_URL` set but no `gh` GitLab auth.
